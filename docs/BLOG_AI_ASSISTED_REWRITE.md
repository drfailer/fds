# Rewriting a 160,000-Line Fortran Simulation with an AI Coding Assistant

## The Challenge

We recently undertook an ambitious project: porting a large-scale Fortran simulation to Hedgehog, a C++20 dataflow graph library developed by our team. The simulation contains roughly 160,000 lines of Fortran 2018, with MPI parallelization, complex physics modules, and decades of accumulated engineering, and needed to be entirely restructured to be used with Hedgehog.

Neither the simulation nor Hedgehog are mainstream technologies. The simulation uses domain-specific numerical methods, deeply nested module dependencies, and Fortran idioms that don't map cleanly to any standard pattern. Hedgehog is a research library with its own conventions around dataflow graphs and thread management, and is mainly used within our group at NIST. Neither would have been well-represented in a language model's training data.

We decided to use an AI coding assistant (specifically Claude Code) to help with this effort. What follows is an honest account of what worked, what didn't, and what we learned about using AI on a project where the AI can't fall back on memorized patterns.

## The Method: Two Modes of Working

We found that productive AI-assisted development requires switching deliberately between two modes.

**Reasoning mode.** In this mode, the AI is asked to read and reason about the code base. The objective is either to improve the developer's understanding of the code (data flows, module dependencies, etc.), or to plan code addition or transformation. When reasoning about the code, the developer may ask the AI to write summaries and documentation that can be reused with future prompts, or simply make some generic queries on the code. It is important to keep in mind that the AI has a coarse-grained view of the code, and asking too specific queries will not work. For instance, asking the AI to list the references to a global variable will either produce a non-accurate listing (because the AI missed some of the symbols), or the AI will start writing its own micro-compiler which will cost time and tokens. To avoid these kind of behavior, the developer should hint the AI to use external tools (for instance, using `callgrind` when the AI needs to reason about function dependencies). When planning, the developer explains what should be done and why it should be done and uses the AI to determine a strategy. Note that Claude Code has a built-in planning mode which is sometimes activated automatically by the AI, however, we noticed that it is better to clearly specify to the AI when it must make a change or simply plan it.

**Editing mode.** In this mode, the AI will be asked to add or refactor existing code. The developer should specify as many constraints as possible to the AI, and make sure the edition is focused on a specific part of the code. A good prompt would start by describing the AI why the change happens, what it will do, and how it will do it, and the AI should always be asked to do a single task. For instance, asking the AI to solve the entire project on its own will always fail, even if the prompt is super specific. On large code bases, the AI will have memory issues and get lost, therefore, the developer should decompose the work manually. The developer should first think about how he would solve a specific problem, where he would start, and then explain it to the AI. Splitting the work into steps solves the AI's memory issues and also allows to extract generic workflows that can be reused later to solve similar problems (see the auto-prompting technique below).

## Productivity Techniques

Over the course of the project, we developed several techniques that dramatically improved throughput.

**Skills.** Claude Code supports "skills" — persistent reference documents that the AI consults when working. We provided a skill document describing the target library's API and conventions. During the project, each time the AI made mistakes related to how it uses the library, we made it fix the issue and record the correction. After completing each important step of the project, we asked the AI to revise its skill to incorporate new knowledge, including the different mistakes it had made and how they were resolved. Over time, the skill evolved from a basic API reference into a comprehensive guide covering named design patterns, failure modes with concrete symptoms and fixes, and integration techniques that were not documented anywhere before. The skill became a living artifact that improved with use — each debugging session made future sessions more efficient.

**Auto-prompting and method files.** The restructuring required the same type of transformation applied to many different parts of the codebase. When we anticipated that a task would need to be repeated, we designed our interaction so that a generic workflow could be extracted once the first instance was complete. The approach works in three phases. First, the developer solves one case interactively with the AI, correcting it as needed, and then asks it to generate a method file — a step-by-step protocol describing the transformation. Second, the AI scans the codebase for other candidate regions where the same method applies, and produces a progress file containing the list of candidates and a reference to the method. Third, the progress file is used to drive the AI through the remaining transformations one by one. This turned what would have been weeks of manual refactoring into a systematic, largely automated process. The progress file also served as a checkpoint: if context was lost or compacted, the AI could read it to resume exactly where it left off. Both method and progress files could be updated at any point to handle edge cases discovered along the way.

**Manual context compaction.** AI coding assistants have finite context windows. On a codebase this large, the context fills up quickly. We learned to plan work in discrete chunks, create or update the progress file at the end of each chunk, and manually compact the context before starting the next one. This prevented the AI from losing track of the overall plan mid-execution, and ensured that each fresh context started with a clear picture of what remained.

**Precise prompting.** The single biggest productivity lever was prompt quality. Effective prompts specify not only what to do, but why, how, which problems the AI might encounter, which method to follow, and what the developer is unsure about. The developer's uncertainty, when made explicit, becomes the AI's investigation task rather than a source of silent errors.

## The Numbers

The throughput of this project would be difficult to explain without AI assistance. Over the course of roughly four working days, we produced 42 commits touching 138 files across two languages, restructuring nearly 78,000 lines of code (46,000 inserted, 31,000 deleted). The work involved decomposing a monolithic 23,000-line module into 12 focused sub-modules, extracting thread-safe computation kernels from 10 different physics modules, constructing 11 parallel dataflow sub-graphs with their associated data structures and interface layers, and setting up a test infrastructure that verified byte-identical numerical results after every change.

Each individual transformation — isolating a computation routine, converting its internal references to use explicit data structures, updating every call site across the codebase, adjusting the build system, and verifying correctness — is a careful, error-prone task that a developer might normally spend half a day on. We completed over a dozen such transformations, along with the module decomposition and the parallel graph construction, in the time it would normally take to do two or three by hand. The AI did not make the work trivial: every transformation still required review, and several subtle bugs required human insight to diagnose. But the mechanical throughput — reading large amounts of code, applying systematic transformations, maintaining consistency across dozens of files — was dramatically accelerated. The developer's time shifted from writing code to directing and verifying, which proved to be a fundamentally more efficient use of domain expertise.

## What AI Cannot Do

Despite these productivity gains, we have a clear-eyed view of the limitations.

**The AI does not understand what it is doing.** It can analyze large volumes of code quickly, but it has no model of the underlying physics, no intuition for numerical stability, and no judgment about architectural trade-offs. When it encountered a routine that mixed independent computation with inter-module data exchange, it could not determine on its own which parts were safe to parallelize and which had to remain sequential. That decision required understanding the application's data dependencies — knowledge that lives in the developer's head, not in the source code.

**AI is a performance multiplier, not a replacement.** A skilled developer who knows the codebase and the target framework can use AI to work several times faster on mechanical transformations. But the multiplier applies equally in both directions: a developer who does not understand the relevant language semantics, thread safety requirements, or framework design constraints will produce incorrect code faster, compounding errors with each iteration. The AI amplifies whatever skill level the developer brings.

**The developer must work harder, not less.** Using AI effectively on a niche project requires more discipline, not less. The developer must decompose work into precise, constrained steps, write detailed prompts, and review every output for correctness. Beyond that, the developer should invest time in thinking about how to make the AI work efficiently — structuring the interaction, maintaining reference documents, designing reusable workflows. Leaving the AI without clear and precise supervision leads to wasted tokens and unusable output. The cognitive load shifts from writing code to directing an agent, and directing well demands a deeper understanding of the problem than simply coding a solution would.

**Nothing replaces domain expertise.** The critical breakthroughs in this project — identifying that a widely-used initialization routine sets global pointer aliases that are fundamentally incompatible with multi-threaded execution, understanding that removing an existing parallelization layer from computation kernels would resolve a class of nested concurrency crashes, recognizing that a synchronization node must impose deterministic ordering on its outputs to guarantee reproducible results — all originated from the developer. The AI executed the resulting fixes efficiently, but it did not and could not have discovered them. These insights require understanding *why* code exists, not just *what* it does, and that understanding remains firmly in the domain of human expertise.

## Conclusion

AI coding assistants are genuinely useful for large-scale code transformation projects, even on niche codebases with non-standard tools. The key is to treat the AI as a powerful but literal-minded collaborator: effective at synthesizing information from large contexts, fast at mechanical transformation, and entirely dependent on clear human direction. The developer's role evolves from writing every line to architecting the approach, constraining the work, and validating the results. The code still needs to be correct. The architecture still needs to be sound. The developer still needs to be good at their job — arguably better than before, because the cost of a wrong direction is amplified by the speed at which the AI can execute it.

The tools are real. The productivity gains are real. But they belong to the developers who know what they're building and why.
